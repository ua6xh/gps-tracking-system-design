# ADR-004: Выбор хранилища для треков (PostgreSQL vs TimescaleDB vs ClickHouse)

**Статус:** Утвержден

## 1. Контекст

Система записывает ~20k GPS-точек/сек (пик 60k). Объём — ~95 ТБ/год при хранении за 12 месяцев. Основной паттерн чтения — point query: получить трек конкретной смены (1000–5000 точек). Аналитика (агрегаты, средняя скорость) вне скоупа MVP.

Нужно хранилище для горячих данных (последний месяц), холодные данные уезжают в BigQuery (см. ADR-002).

## 2. Рассмотренные варианты

### PostgreSQL

Партиционирование по месяцам (`locations_2026_01`, ...), BRIN-индекс на `created_at` (compact, идеален для append-only), B-tree на `(shift_id, created_at)` для point query трека смены.

- ✅ Полноценные транзакции, FK, JOIN
- ✅ Batch INSERT (micro-batching из Kafka consumer, multi-row VALUES) — 20k RPS
- ✅ BRIN-индекс компактный и идеален для time-ordered append-only данных
- ✅ Зрелая экосистема: Patroni, pgbouncer, logical replication
- ✅ Горизонтальное масштабирование через Citus (open source)
- ✅ BigQuery получает данные параллельно из Kafka (BQ Sink Connector), перекладка из PG не нужна
- ❌ Нет нативной компрессии — 95 ТБ/год занимают полный объём
- ❌ Требует ручного управления партициями (создание, DROP)

### TimescaleDB

Расширение PostgreSQL. Hypertables с автоматическими chunk'ами по времени, нативная компрессия (columnar, 10–20x), continuous aggregates, retention policy.

- ✅ Это PostgreSQL внутри — тот же SQL, pgbouncer, Patroni
- ✅ Компрессия 10–20x: 95 ТБ → ~5–10 ТБ сжатых данных
- ✅ Автоматический retention: `add_retention_policy(..., INTERVAL '1 year')`
- ✅ Continuous aggregates — удобны для аналитики (вне скоупа, но пригодятся в будущем)
- ❌ **Компрессированные chunk'и — read-only.** Нельзя удалить отдельную точку (GPS glitch, дубли из batch retry). Нужно decompress → delete → compress — дорогая операция при 20k RPS
- ❌ **Multi-node — платная фича (deprecated).** При масштабировании до 1 млн курьеров горизонтальный шардинг доступен только в Timescale Cloud. Вендорный lock-in
- ❌ Continuous aggregates — главная фича, но наш паттерн (point query трека) её не использует

### ClickHouse

Колоночная OLAP СУБД. MergeTree engine, LZ4-компрессия, горизонтальное масштабирование.

- ✅ Максимальная компрессия (10–30x)
- ✅ Аналитические запросы на миллиардах строк
- ✅ Нативный горизонтальный шардинг
- ❌ **Point queries — не OLAP-паттерн.** SELECT трека одной смены (5000 строк по ключу) — ClickHouse оптимизирован под full-scan, а не lookup
- ❌ **Нет транзакций** — eventual consistency, INSERT может потеряться без подтверждения
- ❌ **INSERT только батчами** (рекомендация 1000+ строк) — дополнительное ограничение
- ❌ **Отдельный стек** — свой кластер, свои runbook'и, другой SQL-диалект, нет pgbouncer/Patroni
- ❌ Нет FK, JOIN'ы медленные — связь с shifts/couriers только через денормализацию

## 3. Сравнение

| Критерий | PostgreSQL | TimescaleDB | ClickHouse |
|---|---|---|---|
| Write 20k RPS | ✅ micro-batch из Kafka | ✅ оптимизирован | ⚠️ только батчами |
| Point query (трек смены) | ✅ BRIN + partition pruning | ✅ chunk pruning | ❌ не OLAP-паттерн |
| Компрессия | ❌ нет нативной | ✅ 10–20x | ✅ 10–30x |
| Мутация данных (DELETE дублей) | ✅ стандартный DELETE | ❌ decompress → delete → compress | ❌ async mutations |
| Масштабирование до 1 млн | ✅ Citus (open source) | ❌ multi-node платный/deprecated | ✅ нативные шарды |
| Транзакции | ✅ | ✅ | ❌ |
| Операционная сложность | ✅ стандартный стек | ⚠️ +extension, ограничения компрессии | ❌ отдельный кластер |

## 4. Решение

**PostgreSQL** с партиционированием по месяцам и BRIN-индексами.

- **ClickHouse** отклонён — наш основной read-паттерн (point query трека смены) не является OLAP-нагрузкой. Отсутствие транзакций и другой операционный стек добавляют сложность без выигрыша.
- **TimescaleDB** отклонён — компрессия полезна, но read-only chunk'и создают проблемы при удалении дублей/мусорных точек. Multi-node масштабирование — платная фича с вендорным lock-in. Continuous aggregates не нужны в нашем паттерне.
- **PostgreSQL** даёт полный контроль над стратегией хранения, прозрачное партиционирование и зрелый стек инструментов. Проблема объёма (95 ТБ/год) решается hot/cold split с BigQuery (ADR-002), а не компрессией на уровне СУБД.

## 5. Последствия

- Нет нативной компрессии — hot storage (~8 ТБ/мес) требует достаточного дискового пространства
- Нужен процесс создания/удаления партиций (cron или pg_partman)
- BigQuery заполняется параллельно через Kafka (BQ Sink Connector), перекладка из PG не требуется
- При масштабировании до 1 млн — шардирование через Citus или ручное по courier_id
