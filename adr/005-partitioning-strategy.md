# ADR-005: Стратегия партиционирования таблицы locations

**Статус:** Утвержден

## 1. Контекст

Таблица `locations` в Tracks DB получает ~1.3 млрд строк в сутки (~260 ГБ/сутки). Hot storage ограничен одним месяцем, после чего данные удаляются из PostgreSQL (параллельно они поступают в BigQuery через Kafka). Нужна стратегия партиционирования, обеспечивающая быстрое удаление старых данных и эффективные запросы.

## 2. Рассмотренные варианты

| Критерий | RANGE по `client_timestamp` (помесячно) | HASH по `courier_id` | RANGE по `shift_id` |
|----------|-----------------------------------|----------------------|---------------------|
| Удаление старых данных | DROP PARTITION — мгновенно (O(1)) | DELETE по всем партициям — медленно, bloat | Нет временных границ — невозможно |
| Partition pruning | По дате — запрос попадает в 1-2 партиции | По courier_id — только если фильтр по courier_id | По shift_id — только если фильтр по shift_id |
| Запрос трека смены | B-tree индекс `(shift_id, client_timestamp)` — эффективно. Смена ~14ч, попадает в 1 партицию (редко в 2 — на стыке месяцев) | Данные смены в одной партиции (один courier_id) | Идеально — одна партиция |
| BRIN-индекс | Работает — данные физически упорядочены по времени | Не работает — порядок записи не совпадает с courier_id | Не работает — shift_id не монотонно упорядочен в записи |
| Совместимость с hot/cold | Естественное разделение: партиция = месяц = единица очистки | Нет связи с временем | Нет связи с временем |

## 3. Решение

**RANGE-партиционирование по `client_timestamp` (помесячно).** Партиции создаются заранее (на 3 месяца вперёд), cron job раз в месяц удаляет партиции старше 1 месяца через DROP PARTITION.

Запросы трека смены эффективны за счёт B-tree индекса `(shift_id, client_timestamp)` — составной индекс позволяет найти строки по `shift_id` и отдать их отсортированными по времени без дополнительного Sort. Смена (макс. ~14ч) практически всегда попадает в одну партицию.

## 4. Последствия

- Партиции нужно создавать заранее (автоматизация через cron или pg_partman)
- DROP PARTITION — мгновенное удаление без vacuum и bloat
- BRIN-индекс на `client_timestamp` занимает ~МБ вместо десятков ГБ (B-tree) при 1.3 млрд строк/сутки
- Запросы по `shift_id` работают через B-tree индекс, не через партиционирование
