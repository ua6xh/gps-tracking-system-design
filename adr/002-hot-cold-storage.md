# ADR-002: Стратегия хранения треков (Hot/Cold)

**Статус:** Утвержден

## 1. Контекст

Система генерирует ~260 ГБ GPS-данных в сутки, ~95 ТБ в год. Хранить всё в одной PostgreSQL — дорого и неэффективно. Требования к latency для свежих и исторических данных различаются.

## 2. Рассмотренные варианты

| Критерий | Всё в PostgreSQL | PostgreSQL + партиции | PostgreSQL (hot) + BigQuery (cold) |
|----------|-----------------|----------------------|-----------------------------------|
| Стоимость хранения | Высокая (95 ТБ SSD) | Высокая | Низкая (BQ — колоночное сжатие) |
| Latency hot данных | Хорошая | Хорошая | Хорошая |
| Latency cold данных | Деградирует с ростом | Средняя | 1-3 сек (приемлемо) |
| Сложность | Низкая | Низкая | Средняя (фоновый процесс, роутинг) |
| Масштабируемость | Плохая | Средняя | Хорошая |

## 3. Решение

**PostgreSQL с партиционированием по месяцам (hot, 0-1 месяц) + BigQuery (cold, 1-12 месяцев).** Данные попадают в оба хранилища параллельно: Tracks сервис и BigQuery Sink Connector — два независимых consumer group'а на одном Kafka-топике `raw-locations`. Перекладка PG → BQ не нужна.

Очистка hot storage — cron job раз в месяц выполняет `DROP PARTITION` для партиций PG старше 1 месяца. Retention топика `raw-locations` — 7 дней (запас на случай падения Sink Connector'а).

Роутинг запросов в Couriers сервисе через два адаптера за единым интерфейсом, выбор по дате смены.

## 4. Последствия

- BigQuery Sink Connector (Kafka Connect) — дополнительный компонент инфраструктуры
- Retention `raw-locations` увеличен до 7 дней для отказоустойчивости BQ-pipeline
- Роутинг в сервисе добавляет сложность, но прозрачен для клиента
- Latency для cold данных выше (1-3 сек vs <100 мс), но для просмотра истории приемлемо
- Стоимость хранения снижается в разы
- Нет ETL-процесса перекладки — архитектура проще
