    PRD — Система GPS-трекинга курьеров¶

    Ответственный: Вячеслав Мельников

    1. Контекст продукта¶

    MeepMeep — федеральный логистический оператор, работающий по всей РФ. Компания обслуживает доставку посылок, документов и еды. Уже существует курьерская сеть, внутренние IT-системы (заказы, склады, CRM). Трекинг курьеров до сих пор работал через сторонний SaaS, который не устраивает по функционалу (нет привязки треков к заказам, слабая аналитика) и стоимости (оплата за курьера/месяц при 500k курьеров — неоправданно дорого). Принято решение строить собственную систему GPS-трекинга как внутренний сервис, интегрированный с мобильным приложением курьера и веб-интерфейсом диспетчера.

    2. Проблема¶

    Текущий SaaS-трекинг не покрывает потребности бизнеса: нет привязки маршрутов к заказам, невозможно анализировать эффективность курьеров, стоимость растёт линейно с количеством курьеров. Диспетчеры вынуждены переключаться между системами, теряя время и контекст.

    3. Цель инициативы¶

    Создать собственную систему GPS-трекинга, которая позволит диспетчерам в реальном времени отслеживать курьеров, просматривать маршруты в привязке к сменам и заказам, и хранить историю перемещений для аналитики.

    4. Целевая аудитория¶

    • Курьер — мобильное приложение, источник GPS-данных. Выходит на линию, принимает заказы, доставляет, уходит с линии.
    • Диспетчер/оператор — веб-интерфейс, потребитель данных. Смотрит карту, анализирует маршруты, контролирует смены.

    Конечный клиент (получатель посылки/еды) — вне скоупа. Клиентское приложение и система заказов уже существуют и работают, трекинг интегрируется с ними через внутренние API.

    5. Ключевые возможности¶

    Курьер:

    • Выход на линию / уход с линии (управление сменой)
    • Принятие заказа / завершение заказа
    • Автоматическая отправка GPS-координат каждые 10 секунд
    • Буферизация точек при потере связи, отправка при восстановлении

    Диспетчер:

    • Карта с курьерами в видимой области (bounding box)
    • Обновление позиций на карте (polling каждые 5 сек)
    • Список курьеров с фильтрацией по статусу
    • Список смен курьера с фильтрацией по дате
    • Просмотр трека смены на карте с выделением участков по заказам
    • Просмотр трека конкретного заказа

    6. Скоуп работ и этапы¶

    Этап 1 — Трекинг (MVP): Смены + непрерывный трек GPS-точек. Карта, история, мониторинг. Полная архитектура write/read path.

    Этап 2 — Заказы: Сущность "заказ" внутри смены. Привязка участков трека к заказам. API для получения трека заказа. Визуализация на карте.

    7. Что НЕ входит в скоуп¶

    • Клиентское приложение получателя (отслеживание курьера клиентом)
    • Назначение заказов на курьеров (внешняя система)
    • Построение маршрутов / навигация
    • Расчёт ETA (Estimated Time of Arrival)
    • Пуш-уведомления
    • Чат курьер-клиент / курьер-диспетчер
    • Биллинг, мультитенантность
    • Авторизация / аутентификация

    8. Открытые вопросы¶

    Вопрос Влияние
    Нужна ли интерполяция позиции на клиенте для плавного отображения? UX, фронтенд-сложность. Не влияет на архитектуру.
    Какой retention для горячих данных (неделя, месяц)? Решено: 1 месяц в PostgreSQL, далее BigQuery (см. ADR-002)
    Как внешняя система заказов интегрируется с трекингом? Контракт интеграции, этап 2

    9. Метрики успеха¶

    • Staleness — задержка отображения данных на карте < 1 минуты
    • Availability — 99.99% (четыре девятки)
    • Data loss — потеря GPS-точек < 0.1%
    • Latency — отклик API карты < 200 мс (p95)

    10. Риски¶

    Риск Митигация
    Потеря GPS-данных при проблемах со связью у курьера Буферизация на клиенте, батчевая отправка
    Высокая write-нагрузка (20k RPS) перегружает хранилище Write-optimized хранилище, буферизация на сервере
    Объём исторических данных (~95 ТБ/год) Разделение на горячее/холодное хранение
    Сезонные пики (x3 от среднего) Эластичная архитектура, автоскейлинг
    Зависимость от внешней системы заказов (этап 2) Асинхронная интеграция через события, слабая связность
