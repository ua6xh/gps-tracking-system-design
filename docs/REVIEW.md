## Critical

### C-1. Числовая ошибка: 1.3 млрд/сутки vs 1.3 млрд/мес

**Кто нашёл:** Infra Architect

**Файлы:** ADR-005:7, ADR-005:29, SAD:169

**Проблема:** В SAD расчёт верный: 200k × 6 × 60 × 18 ≈ **1.3 млрд/сутки** (~260 ГБ/сутки). Но в ADR-005 написано "~1.3 млрд строк в месяц (~260 ГБ/мес)", а в SAD:169 — "1.3 млрд строк/месяц". Ошибка в 30 раз влияет на все оценки размеров индексов и дисков.

**Рекомендация:** Исправить на "~1.3 млрд строк/сутки" или "~39 млрд строк/месяц".

**Решение:** Исправлено. Все вхождения заменены на "1.3 млрд строк/сутки" (SAD, ADR-005).

### C-2. Таблица locations не имеет Primary Key

**Кто нашёл:** Data Architect

**Файл:** SAD:160-166

**Проблема:** PK не определён. В PG партиционированная таблица требует, чтобы PK включал ключ партиционирования. Без PK невозможна дедупликация (при at-least-once семантике Kafka дубли неизбежны). В ADR-004 упоминается "удаление GPS glitch" как преимущество PG, но без unique constraint это невозможно.

**Рекомендация:** Добавить составной PK или UNIQUE: `(shift_id, created_at)` или суррогатный `bigserial` + `created_at`. Если PK сознательно отсутствует — задокументировать стратегию дедупликации.

**Решение:** Без PK — осознанный trade-off. Записи append-only, удаление только DROP PARTITION, единичные дубли при batch retry допустимы. PK/UNIQUE на 1.3 млрд строк/сутки замедлил бы INSERT без пользы. Задокументировано в SAD.

### C-3. FK constraints между разными PG-инстансами невозможны

**Кто нашёл:** Data Architect, Infra Architect

**Файл:** SAD:162-163

**Проблема:** `locations.shift_id FK→shifts` и `locations.courier_id FK→couriers` — но `locations` в Tracks DB, а `shifts`/`couriers` в Couriers DB. Cross-database FK в PostgreSQL невозможны.

**Рекомендация:** Убрать `FK→` пометки из Tracks DB. Добавить примечание: "Ссылочная целостность обеспечивается на уровне приложения".

**Решение:** Исправлено. FK убраны из Tracks DB, добавлено пояснение: логические связи, целостность на уровне приложения (данные из Kafka с валидированными идентификаторами).

## Major

### M-1. Нет мониторинга BQ Sink Connector

**Кто нашёл:** Infra Architect

**Файл:** SAD:276-299

**Проблема:** Если BQ Sink Connector молча отстаёт, данные не попадают в cold storage. Через месяц PG-партиция дропается → данные потеряны навсегда.

**Рекомендация:** Добавить алерт на consumer lag группы `bq-sink`. Warning: lag растёт 15 мин. Critical: lag растёт 1 час.

**Решение:** Исправлено. Алерт добавлен в таблицу. Мониторинг переработан: RED для сервисов, USE для инфраструктуры.

---

### M-2. Нет pre-check перед DROP PARTITION

**Кто нашёл:** Infra Architect

**Файл:** ADR-002, SAD:86

**Проблема:** DROP PARTITION выполняется по расписанию. Нет проверки, что данные доехали в BigQuery. Если BQ Sink Connector отстал >7 дней (retention Kafka), данные потеряны.

**Рекомендация:** Добавить проверку: lag consumer group `bq-sink` = 0 перед дропом. Либо описать как допустимый риск.

**Решение:** Исправлено. Pre-check добавлен: cron проверяет lag `bq-sink` перед дропом, если lag > 0 — дроп не выполняется, алерт.

---

### M-3. Механизм восстановления Redis не описан

**Кто нашёл:** Infra Architect

**Файл:** SAD:249, ADR-003

**Проблема:** Написано "восстановление из потока Kafka за секунды", но КАК — не описано. Couriers сервис читает `last-coordinate` с committed offset, не replay'ит историю.

**Рекомендация:** Описать: при failover Redis просто ждём ~10 сек — все 200k курьеров пришлют свежие координаты естественным потоком (интервал 10 сек). Явно задокументировать.

**Решение:** Исправлено. Уточнено в SAD: Couriers сервис продолжает GEOADD из потока Kafka, позиции восстанавливаются за ~10 сек, replay не нужен.

---

### M-4. Redis Geo: нет cleanup при закрытии смены

**Кто нашёл:** Data Architect, Infra Architect

**Файл:** SAD:179

**Проблема:** Не описан `ZREM` при закрытии смены. Курьеры-"призраки" будут отображаться на карте. Также нет защиты от "зависших" курьеров (потеря связи).

**Рекомендация:** Описать: (1) `ZREM couriers:active {courier_id}` при закрытии смены, (2) фоновая задача удаляет курьеров без обновления >5 мин.

**Решение:** Исправлено. Добавлено: GEOADD как upsert, ZREM при закрытии смены, `couriers:last_seen` HSET, фоновая задача удаления "призраков" (last_seen > 5 мин).

### M-5. float вместо double precision для координат

**Кто нашёл:** Data Architect

**Файл:** SAD:164-165

**Проблема:** `float` (real, 4 байта) даёт ~6-7 значащих цифр. Координата 55.755814 — 8 цифр. Погрешность 1-10 метров.

**Рекомендация:** Использовать `double precision` (float8). Добавляет 8 байт/строку (~10 ГБ/мес) — незначительно.

**Решение:** Исправлено. `float` → `double precision` в SAD.

### M-6. Нет индекса для запроса трека заказа

**Кто нашёл:** Data Architect

**Файл:** SAD:155

**Проблема:** Запрос трека заказа: `WHERE courier_id = ? AND created_at BETWEEN ...`. Индекс `(shift_id, created_at)` не поможет — запрос по `courier_id`.

**Рекомендация:** Перестроить запрос: сначала найти `shift_id` через `orders.shift_id`, затем использовать существующий индекс `(shift_id, created_at)`. Дополнительный индекс не нужен.

**Решение:** Исправлено. Запрос перестроен: `WHERE shift_id = ? AND created_at BETWEEN ...`, shift_id из orders.

### M-7. BigQuery без CLUSTER BY

**Кто нашёл:** Data Architect

**Файл:** SAD:172-175

**Решение:** Исправлено. Добавлены PARTITION BY и CLUSTER BY с обоснованием стоимости запросов.

### M-8. Отсутствие accuracy в locations

**Кто нашёл:** Data Architect

**Файл:** SAD:160-166

**Проблема:** GPS-чип всегда отдаёт accuracy (точность в метрах). Без этого поля невозможно фильтровать мусорные точки (GPS glitch в здании, accuracy >100м).

**Рекомендация:** Добавить `accuracy` (float). Опционально `speed` (float). +4-8 байт/строку.

**Решение:** Исправлено. Добавлено поле `accuracy` (float, метры). `speed` — за скоупом MVP.
