## Critical

### C-1. Не описан механизм привязки GPS-точки к `shift_id`

**Источник:** Data Architect, API Architect

Таблица `locations` содержит `shift_id`, но:

- Courier API (`LocationInput`) не принимает `shift_id`
- Location Ingester "не ходит в БД"
- Tracks сервис должен как-то определить текущую смену курьера

Непонятно, как GPS-точка ассоциируется со сменой на write path. Это ключевой gap в описании архитектуры.

### C-2. Поле `accuracy` отсутствует в обоих API

**Источник:** API Architect, Data Architect, Content Specialist

SAD определяет `accuracy` в таблице `locations` и описывает фильтрацию (`accuracy > 100м` — игнорируется). Но ни `LocationInput` (Courier API), ни `Location` (Operator API) не содержат этого поля. Разрыв между архитектурой и API-контрактом.

### C-3. Нет описания среды деплоя

**Источник:** Infra Architect

Нигде не указано: Kubernetes / bare metal / VM, облако / on-premise, стратегия деплоя (rolling, blue-green, canary), CI/CD, количество инстансов, resource requests/limits. DevOps-команда не может начать работу по этому SAD.

## Major

### M-1. Схема `Error` слишком примитивна

**Источник:** API Architect

Текущий формат (`error: string`) не позволяет клиенту программно различать типы ошибок. Рекомендуется структура с `code` (машиночитаемый) + `message` (человекочитаемый).

### M-2. `DELETE /shifts/{shiftId}` — семантическое несоответствие

**Источник:** API Architect

Закрытие смены не удаляет ресурс — смена продолжает существовать. Семантически корректнее `POST /shifts/{shiftId}/close`.

### M-3. Нет ограничения на размер bounding box

**Источник:** API Architect, Infra Architect

Запрос с координатами всей России вернёт все 200k курьеров. Потенциальный DoS-вектор и тяжёлый запрос для Redis.

### M-4. Partition pruning по `shift_id` невозможен

**Источник:** Data Architect

RANGE-партиционирование по `created_at` не позволяет PostgreSQL выполнить pruning по `shift_id`. Запрос идёт по B-tree индексу в каждой живой партиции. Рекомендуется добавлять `created_at` range в запрос.

### M-5. Edge case hot→cold: смена на стыке месяцев

**Источник:** Data Architect

Смена 31 января 23:00 → 1 февраля 13:00. После дропа январской партиции часть данных в PG, часть в BigQuery. Роутинг и дедупликация не описаны.

### M-6. `timestamp` (API) vs `created_at` (DB) — семантическое несоответствие

**Источник:** Data Architect, Content Specialist

`timestamp` — время фиксации GPS на устройстве, `created_at` — время создания записи в БД. Если хранится клиентское время, имя `created_at` вводит в заблуждение. Стоит хранить оба или переименовать.

### M-7. Дубликаты при batch retry попадают в BigQuery

**Источник:** Data Architect

Для визуализации трека дубли незаметны, но для аналитики (этап 2) влияют на расчёты. Нет стратегии дедупликации.

### M-8. GEOSEARCH BYBOX принимает width/height, а не координаты углов

**Источник:** Data Architect

API принимает два угла bounding box, Redis — ширину/высоту в км. Требуется пересчёт, нетривиальный на больших широтах. Не описан.

### M-9. Cookie auth без упоминания CSRF-защиты

**Источник:** API Architect

JWT в httpOnly cookie — хороший выбор, но при добавлении мутирующих эндпоинтов (этап 2+) потребуется CSRF-токен. Стоит явно указать.

### M-10. 3 Kafka-брокера мало для 99.99% при пиковых нагрузках

**Источник:** Infra Architect

При падении одного из трёх брокеров нагрузка на оставшиеся два резко возрастает. С RF=3 и двумя consumer groups — недостаточный запас. Рекомендуется минимум 5.

### M-11. Не указаны параметры micro-batching в PG

**Источник:** Infra Architect

Размер batch, интервал flush, реальное число INSERT/sec на мастер — без этих параметров невозможно оценить нагрузку на PostgreSQL.

### M-12. Redis Sentinel не детализирован

**Источник:** Infra Architect

Не описано: количество Sentinel-нод, quorum, время failover (типичное 30-60 сек — карта недоступна), стратегия для Redis Cache vs Redis Geo.

### M-13. BQ Sink Connector — SPOF cold path

**Источник:** Infra Architect

Единственный путь данных в cold storage. Нет описания HA-конфигурации Kafka Connect, runbook при отставании > 7 дней.

### M-14. Не указан стек мониторинга

**Источник:** Infra Architect

Метрики RED/USE и алерты описаны, но не указано через что: Prometheus? Grafana? Loki? Jaeger? Без этого раздел мониторинга — декларация намерений.

### M-15. Нет DR-процедур, RTO/RPO, бэкап-стратегии

**Источник:** Infra Architect

Не описаны процедуры восстановления при потере PG, Redis, Kafka. Нет бэкап-стратегии для PG Couriers.

### M-16. Нет сетевой топологии

**Источник:** Infra Architect

Не описано: публичный LB, TLS-терминация, service mesh, сегментация сети.

## Анализ и рекомендации

### Паттерны замечаний

**1. Поле `accuracy` — сквозная проблема (C-2)**

Найдено тремя агентами независимо. Это самое частое замечание: поле есть в БД, используется для фильтрации, но отсутствует в обоих API. Исправление простое — добавить в `LocationInput` и `Location`.

**2. Привязка GPS-точки к смене (`shift_id`) — архитектурный gap (C-1)**

Найдено двумя агентами. Ключевой вопрос write path: откуда берётся `shift_id`? Наиболее логичное решение — Tracks сервис определяет текущую открытую смену по `courier_id` (кэшируя маппинг). Это нужно явно описать.

**3. Инфраструктурная детализация (C-3, M-10..M-16)**

Infra Architect нашёл больше всего Major-замечаний. Большинство касаются не архитектурных ошибок, а недостаточной детализации для DevOps: среда деплоя, стек мониторинга, DR-процедуры, сетевая топология. Для учебного проекта это допустимо — стоит добавить хотя бы краткий раздел "Deployment Overview".

**4. Консистентность между документами (M-6, m-3, m-21)**

Content Specialist нашёл несколько расхождений в числах и терминах между SAD и ADR. Легко исправить, но важно для защиты.

### Что исправить обязательно (перед защитой)

1. **C-1:** Описать в SAD механизм привязки `shift_id` на write path
2. **C-2:** Добавить `accuracy` в оба API (input + output)
3. **M-6:** Уточнить семантику `timestamp` vs `created_at`
4. **m-3:** Синхронизировать "3 месяца вперёд" / "на месяц вперёд"
5. **m-5:** Уточнить обоснование допустимости потерь при acks=1
6. **s-1:** Пересчитать стоимость BigQuery ($594, не $0.50)

### Что стоит добавить (усилит документ)

1. Краткий раздел "Deployment Overview" (K8s/cloud, число инстансов)
2. Раздел "DR & Backup" (RTO/RPO, процедуры восстановления)
3. Ограничение bounding box в API (максимальная площадь или limit)
4. `POST /shifts/{shiftId}/close` вместо `DELETE`

### Что можно оставить как есть

- Большинство Minor от Infra Architect — детализация, выходящая за рамки учебного SAD
- Suggestion — улучшения, не влияющие на защиту
- ADR для Kafka/BigQuery — обоснование уже есть в SAD, отдельные ADR необязательны
