    Critical¶

    C-1. Числовая ошибка: 1.3 млрд/сутки vs 1.3 млрд/мес¶

    Кто нашёл: Infra Architect

    Файлы: ADR-005:7, ADR-005:29, SAD:169

    Проблема: В SAD расчёт верный: 200k × 6 × 60 × 18 ≈ 1.3 млрд/сутки (~260 ГБ/сутки). Но в ADR-005 написано "~1.3 млрд строк в месяц (~260 ГБ/мес)", а в SAD:169 — "1.3 млрд строк/месяц". Ошибка в 30 раз влияет на все оценки размеров индексов и дисков.

    Рекомендация: Исправить на "~1.3 млрд строк/сутки" или "~39 млрд строк/месяц".

    Решение: Исправлено. Все вхождения заменены на "1.3 млрд строк/сутки" (SAD, ADR-005).

    C-2. Таблица locations не имеет Primary Key¶

    Кто нашёл: Data Architect

    Файл: SAD:160-166

    Проблема: PK не определён. В PG партиционированная таблица требует, чтобы PK включал ключ партиционирования. Без PK невозможна дедупликация (при at-least-once семантике Kafka дубли неизбежны). В ADR-004 упоминается "удаление GPS glitch" как преимущество PG, но без unique constraint это невозможно.

    Рекомендация: Добавить составной PK или UNIQUE: (shift_id, created_at) или суррогатный bigserial + created_at. Если PK сознательно отсутствует — задокументировать стратегию дедупликации.

    Решение: Без PK — осознанный trade-off. Записи append-only, удаление только DROP PARTITION, единичные дубли при batch retry допустимы. PK/UNIQUE на 1.3 млрд строк/сутки замедлил бы INSERT без пользы. Задокументировано в SAD.

    C-3. FK constraints между разными PG-инстансами невозможны¶

    Кто нашёл: Data Architect, Infra Architect

    Файл: SAD:162-163

    Проблема: locations.shift_id FK→shifts и locations.courier_id FK→couriers — но locations в Tracks DB, а shifts/couriers в Couriers DB. Cross-database FK в PostgreSQL невозможны.

    Рекомендация: Убрать FK→ пометки из Tracks DB. Добавить примечание: "Ссылочная целостность обеспечивается на уровне приложения".

    Решение: Исправлено. FK убраны из Tracks DB, добавлено пояснение: логические связи, целостность на уровне приложения (данные из Kafka с валидированными идентификаторами).

    Major¶

    M-1. Нет мониторинга BQ Sink Connector¶

    Кто нашёл: Infra Architect

    Файл: SAD:276-299

    Проблема: Если BQ Sink Connector молча отстаёт, данные не попадают в cold storage. Через месяц PG-партиция дропается → данные потеряны навсегда.

    Рекомендация: Добавить алерт на consumer lag группы bq-sink. Warning: lag растёт 15 мин. Critical: lag растёт 1 час.

    Решение: Исправлено. Алерт добавлен в таблицу. Мониторинг переработан: RED для сервисов, USE для инфраструктуры.

    M-2. Нет pre-check перед DROP PARTITION¶

    Кто нашёл: Infra Architect

    Файл: ADR-002, SAD:86

    Проблема: DROP PARTITION выполняется по расписанию. Нет проверки, что данные доехали в BigQuery. Если BQ Sink Connector отстал >7 дней (retention Kafka), данные потеряны.

    Рекомендация: Добавить проверку: lag consumer group bq-sink = 0 перед дропом. Либо описать как допустимый риск.

    Решение: Исправлено. Pre-check добавлен: cron проверяет lag bq-sink перед дропом, если lag > 0 — дроп не выполняется, алерт.

    M-3. Механизм восстановления Redis не описан¶

    Кто нашёл: Infra Architect

    Файл: SAD:249, ADR-003

    Проблема: Написано "восстановление из потока Kafka за секунды", но КАК — не описано. Couriers сервис читает last-coordinate с committed offset, не replay'ит историю.

    Рекомендация: Описать: при failover Redis просто ждём ~10 сек — все 200k курьеров пришлют свежие координаты естественным потоком (интервал 10 сек). Явно задокументировать.

    Решение: Исправлено. Уточнено в SAD: Couriers сервис продолжает GEOADD из потока Kafka, позиции восстанавливаются за ~10 сек, replay не нужен.

    M-4. Redis Geo: нет cleanup при закрытии смены¶

    Кто нашёл: Data Architect, Infra Architect

    Файл: SAD:179

    Проблема: Не описан ZREM при закрытии смены. Курьеры-"призраки" будут отображаться на карте. Также нет защиты от "зависших" курьеров (потеря связи).

    Рекомендация: Описать: (1) ZREM couriers:active {courier_id} при закрытии смены, (2) фоновая задача удаляет курьеров без обновления >5 мин.

    Решение: Исправлено. Добавлено: GEOADD как upsert, ZREM при закрытии смены, couriers:last_seen HSET, фоновая задача удаления "призраков" (last_seen > 5 мин).

    M-5. float вместо double precision для координат¶

    Кто нашёл: Data Architect

    Файл: SAD:164-165

    Проблема: float (real, 4 байта) даёт ~6-7 значащих цифр. Координата 55.755814 — 8 цифр. Погрешность 1-10 метров.

    Рекомендация: Использовать double precision (float8). Добавляет 8 байт/строку (~10 ГБ/мес) — незначительно.

    Решение: Исправлено. float → double precision в SAD.

    M-6. Нет индекса для запроса трека заказа¶

    Кто нашёл: Data Architect

    Файл: SAD:155

    Проблема: Запрос трека заказа: WHERE courier_id = ? AND created_at BETWEEN .... Индекс (shift_id, created_at) не поможет — запрос по courier_id.

    Рекомендация: Перестроить запрос: сначала найти shift_id через orders.shift_id, затем использовать существующий индекс (shift_id, created_at). Дополнительный индекс не нужен.

    Решение: Исправлено. Запрос перестроен: WHERE shift_id = ? AND created_at BETWEEN ..., shift_id из orders.

    M-7. BigQuery без CLUSTER BY¶

    Кто нашёл: Data Architect

    Файл: SAD:172-175

    Проблема: "Та же структура locations" — но без кластеризации запрос трека за год (95 ТБ) = full scan. $5/ТБ → один запрос ~$0.50 вместо ~$0.001.

    Рекомендация: Добавить: PARTITION BY DATE(created_at), CLUSTER BY shift_id, courier_id.

    Решение: Исправлено. Добавлены PARTITION BY и CLUSTER BY с обоснованием стоимости запросов.

    M-8. Отсутствие accuracy в locations¶

    Кто нашёл: Data Architect

    Файл: SAD:160-166

    Проблема: GPS-чип всегда отдаёт accuracy (точность в метрах). Без этого поля невозможно фильтровать мусорные точки (GPS glitch в здании, accuracy >100м).

    Рекомендация: Добавить accuracy (float). Опционально speed (float). +4-8 байт/строку.

    Решение: Исправлено. Добавлено поле accuracy (float, метры). speed — за скоупом MVP.

    M-9. Дедупликация при at-least-once не описана¶

    Кто нашёл: Data Architect

    Файл: SAD:58

    Проблема: Kafka at-least-once + consumer rebalance = дубли. Стратегия не описана.

    Рекомендация: Связано с C-2 (PK). При наличии UNIQUE(shift_id, created_at) — INSERT ... ON CONFLICT DO NOTHING.

    Решение: Покрыто C-2. Дубли допустимы, дедупликация не требуется.

    M-10. Ссылка на ADR-004 отсутствует в SAD 4.7¶

    Кто нашёл: Doc Specialist

    Файл: SAD:191-197

    Проблема: ADR-001, 002, 003, 005 перечислены в разделе "Важные решения". ADR-004 (выбор хранилища — одно из ключевых решений) пропущен.

    Рекомендация: Добавить: - **Выбор хранилища для треков** — см. [ADR-004](adr/004-track-storage-choice.md)

    Решение: Исправлено. Ссылка добавлена в SAD 4.7.

    M-11. PLAN.md: retention "2д" не соответствует "7д"¶

    Кто нашёл: Doc Specialist

    Файл: PLAN.md:19

    Проблема: В PLAN написано "retention 2д/24ч", в SAD и ADR-002 — 7 дней.

    Рекомендация: Исправить на "7д/24ч".

    Решение: Исправлено.

    M-12. API: snake_case в SAD vs camelCase в OpenAPI¶

    Кто нашёл: API Architect

    Файлы: SAD:104-117, courier-api.yaml, operator-api.yaml

    Проблема: SAD: {shift_id}, {courier_id}. OpenAPI: {shiftId}, {courierId}. Расхождение naming convention.

    Рекомендация: Привести к единому стилю. camelCase в URL path params — распространённая практика. Обновить SAD или OpenAPI.

    Решение: Исправлено. SAD приведён к camelCase в URL path params ({shiftId}, {courierId}, {orderId}). Поля БД остаются snake_case.

    M-13. API: DELETE /shifts нет 403/400¶

    Кто нашёл: API Architect

    Файл: courier-api.yaml:72

    Проблема: Нет ответа для "попытка закрыть чужую смену" (403) или "смена уже закрыта" (400).

    Рекомендация: Добавить 403 и/или 400 с описанием.

    Решение: Исправлено. Добавлен 409 Conflict ("смена уже закрыта"). 404 уточнён ("не найдена или не принадлежит курьеру"). 403 не нужен — courier_id из токена, чужой shiftId = 404.

    Minor¶

    m-1. Location Ingester не включён в список сервисов¶

    Кто нашёл: Doc Specialist

    Файл: SAD:32-36, 45

    Проблема: Location Ingester описан отдельным абзацем после "Сервисы" и "Хранилища", хотя является сервисом.

    Рекомендация: Включить в список сервисов.

    Решение: Исправлено. Location Ingester перенесён в список сервисов, дублирующий абзац удалён.

    m-2. "slave" vs "replica" — смешение терминологии¶

    Кто нашёл: Doc Specialist

    Файл: SAD:81, 286

    Проблема: PG с версии 14 использует primary/standby. В SAD смешаны "slave" и "реплики".

    Рекомендация: Заменить "slave" на "replica".

    Решение: Оставлено master/slave — терминология принятая в команде.

    m-3. pgbouncer не умеет шардировать¶

    Кто нашёл: Infra Architect

    Файл: SAD:321

    Проблема: "Несколько шардов за pgbouncer" — pgbouncer мультиплексирует соединения, не роутит шарды.

    Рекомендация: Исправить: "Несколько шардов через Citus или ручное шардирование на уровне приложения".

    Решение: Исправлено.

    m-4. Lifecycle партиций не описан¶

    Кто нашёл: Infra Architect

    Файл: SAD:86, ADR-005

    Проблема: Не описано сколько партиций живёт одновременно, когда именно дроп, что если cron упал и партиция не создана (INSERT'ы упадут).

    Рекомендация: Описать: создание на 2-3 месяца вперёд, fallback через pg_partman.

    Решение: Исправлено. Lifecycle описан: создание на 3 месяца вперёд, одновременно живут текущая + прошлый месяц + 3 будущих.

    m-5. Hot storage window плавает 1-2 месяца¶

    Кто нашёл: Data Architect, Infra Architect

    Файл: SAD:82, ADR-005

    Проблема: Помесячные партиции + дроп "старше 1 мес" → данные за начало месяца хранятся ~2 месяца, за конец ~1 месяц. Роутинг по дате на стыке месяцев может отправить в PG, хотя данные уже дропнуты.

    Рекомендация: Явно задокументировать: hot = 1-2 месяца. Или использовать ended_at для роутинга.

    Решение: Исправлено. Задокументировано: hot window 1-2 месяца, роутинг в BQ если смена старше последней живой партиции.

    m-6. BRIN — use-case не описан явно¶

    Кто нашёл: Data Architect

    Файл: SAD:169

    Проблема: Partition pruning PG делает автоматически. BRIN полезен для запросов "все точки за последний час" (мониторинг), но это не описано.

    Рекомендация: Указать конкретный use-case для BRIN.

    Решение: Исправлено. Добавлен use-case: мониторинговые и отладочные запросы по диапазону времени.

    m-7. Нет индекса shifts(courier_id, started_at)¶

    Кто нашёл: Data Architect

    Файл: SAD:115, 152

    Проблема: GET /shifts по courier_id с фильтрацией по дате — partial index покрывает только открытые смены.

    Рекомендация: Добавить B-tree (courier_id, started_at DESC) для пагинации смен.

    Решение: Исправлено. Индекс добавлен в SAD.

    m-8. Redis кэш: HSET vs STRING¶

    Кто нашёл: Data Architect

    Файл: SAD:183

    Проблема: Описан "HSET" для кэша треков, но "массив точек" — это blob, для которого логичнее STRING (SET).

    Рекомендация: Уточнить: если JSON blob → STRING, если structured → описать поля HSET.

    Решение: Исправлено. HSET → STRING. Кэш трека = JSON blob, один SET/GET.

    m-9. API: нет 401 Unauthorized¶

    Кто нашёл: API Architect

    Файлы: courier-api.yaml, operator-api.yaml

    Проблема: Оба API используют аутентификацию, но 401 не описан ни в одном эндпоинте.

    Рекомендация: Добавить 401 как общий response.

    Решение: Исправлено. 401 Unauthorized добавлен на все эндпоинты courier-api.yaml и operator-api.yaml.

    m-10. PLAN.md: camelCase (orderId, courierId)¶

    Кто нашёл: Doc Specialist

    Файл: PLAN.md:46, 51

    Проблема: camelCase в PLAN, snake_case в SAD/ADR.

    Рекомендация: Привести к snake_case.

    Решение: Исправлено. PLAN.md приведён к snake_case.

    m-11. ADR-004: "~8 ТБ/мес" для hot storage¶

    Кто нашёл: Doc Specialist, Infra Architect

    Файл: ADR-004:73

    Проблема: 260 ГБ/сутки × 30 = ~7.8 ТБ/мес — число верное, но расходится с "~260 ГБ/мес" в ADR-005 (который содержит ошибку, см. C-1). После исправления C-1 всё сойдётся.

    Рекомендация: Исправится автоматически при исправлении C-1.

    Решение: Исправлено с C-1.

    m-12. Redis: нет метаданных позиции (last_seen_at)¶

    Кто нашёл: Data Architect

    Файл: SAD:179

    Проблема: Диспетчер не знает, актуальна ли позиция курьера (30 сек или 10 мин давности).

    Рекомендация: Добавить HSET courier:meta:{courier_id} с last_seen_at.

    Решение: Покрыто M-4. Добавлен couriers:last_seen HSET.

    Suggestion¶

    S-1. shifts.id: int → bigint¶

    Кто нашёл: Data Architect. При 1 млн курьеров × 2 смены/день — переполнение int за ~3 года.

    S-2. POST /locations: 200 → 202 Accepted¶

    Кто нашёл: API Architect. Данные пишутся в Kafka асинхронно, 202 точнее семантически.

    S-3. Courier schema: расширить профиль¶

    Кто нашёл: API Architect. GET /couriers/{id} и CourierSummary идентичны — нет смысла в отдельном эндпоинте.

    S-4. POST /shifts: добавить started_at в response¶

    Кто нашёл: API Architect. Мобильному клиенту нужно серверное время начала смены.

    S-5. POST /locations: поведение без открытой смены¶

    Кто нашёл: API Architect. Что если GPS-точка приходит, а смена не открыта? Нужен 400 или тихо игнорировать?

    S-6. ADR для acks=1 vs acks=all¶

    Кто нашёл: Doc Specialist. Серьёзный trade-off, заслуживает отдельного ADR.

    S-7. Метрики micro-batching¶

    Кто нашёл: Infra Architect. batch size (avg/p95), insert latency, throughput — не описаны в мониторинге.
